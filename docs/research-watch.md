# 每日逆向报告研究

一次启动完成“指定上游报告或关键词检索 → DeepSeek 核验报告 → 对照代码 → 独立复核 → 更新首页”，随后退出。系统定时任务负责次日重新启动。旧命令保持兼容，研究功能单独配置。

## 单次运行

复制 `examples/research.json`、`examples/research-llm.yml` 到本机私有配置目录，设置目标仓库、提交身份与 `enabled: true`，通过环境变量提供模型凭证。配置不包含实际密钥。示例默认禁止发布，启用 `publish: true` 后自动提交和普通快进推送 README。

```sh
TermiteRS research run-once --config /etc/termiters/research.json --preview
TermiteRS research run-once --config /etc/termiters/research.json
```

需要 Git、Python 3.10+ 和目标仓库的推送凭据。Windows 可以用 `--python C:/path/to/python.exe` 指定解释器。模型使用现有 TermiteRS HTTP 传输、重试与超时逻辑；模型输出不能执行 shell 命令。

`state_dir` 和 `llm_config` 相对研究 JSON 所在目录解析。服务器建议将 `state_dir` 设置为 `/var/lib/termiters/research`。各轮状态在 `state.sqlite3`，最近执行结果在 `last-run.json`，待发布首页在 `README.preview.md`。预览不会推送，也不会更新用户工作区。

## 固定研究上游（当前推荐）

复制 `examples/research-upstream.json`。该模式明确追踪 `wtfwhs/tengu-decoded`，关闭关键词搜索并清空旧种子列表，每天通过 GitHub API 读取分支提交和版本目录。按数值选择最新报告版本（默认1个目录，可配1至3个），只下载其中 Markdown，不下载或执行 bundle。默认优先指纹、遥测、API 和系统提示词，其余 Markdown 按名称进入队列；也可用 `report_files` 限定文件名。每日默认最多4篇，未处理项落盘，已完成且正文、目标源码未变时不调用模型。

每轮先锁定上游提交，再读取该提交的报告，并核对 Git blob SHA；不能在一轮中混用变化中的分支内容。上游仓库、固定提交、报告路径及报告版本明确传入 DeepSeek 的提取、代码评估和独立复核阶段，同时说明它是用户指定的研究来源，不是 Claude 官方仓库，采用明确的报告版本假设：云端 CLI 为本轮所选报告版本，并按报告描述运行。该前提用于判断网关过滤效果，不再次逆向 CLI 或索取动态抓包，也不代表已检测实际部署版本。仍须逐字核对提取声明与报告一致，不能把最新报告目录当作官方最新发布版本。README 标明追踪来源与本轮读取提交，具体结论链接到被核验的固定提交。

代码评估阶段也读取完整报告，以保留触发条件和环境变量语义。`unfiltered` 可以表示报告明确的 CLI 自发请求未经过网关过滤，必须说明条件与路径，不能说成本地字段透传；`not_triggered`（当前配置不触发）要求报告的必要条件与代码中的禁用证据对应，不等同于已过滤。`unknown` 仅表示影响判断的真实证据缺口，复核不能仅因结论是未知而否决。历史结果保留各自评估前提；旧固定上游结果在重评前标明旧口径。规则变化会使旧研究结果及模型缓存失效，后续按每日上限重评。

默认评估配置为 `evaluation_profile: "unbundle_defaults"`：以 Unbundle 默认部署、固定 CLI 参数和环境白名单为前提，不假定用户启用额外功能或自定义覆盖。先判断默认配置是否会触发发送，再评估可能发送的字段是否经过过滤。无需读取或重置个人网关的凭据和私有配置。

`tracked_upstream.context_reports` 默认示例配置为 `["telemetry.md", "environment-variables.md", "feature-flags.md"]`。执行器在同一版本目录、同一固定提交中读取这些关联报告，即使验收通过 `report_files` 只选择一篇，仍补齐关联正文。关联报告用于评估与复核中的控制函数、环境变量和调用点对应说明，不单独扩大本轮主报告数量。关联报告变化会触发重评；缺失会显式提供给模型，超过 `max_context_bytes`（未配置时128000，三份关联报告示例为256000）明确失败，不静默截断。模型的“不触发”结论必须同时提供报告控制引用与网关代码引用，执行器逐字校验；报告路径可使用本轮已提供的精确固定链接，其他版本或未知链接一律拒绝。引用错误一次反馈所有出错的具体机制和报告，并附相近原文行帮助定位；相近行只作为纠错提示，不能替代逐字校验或自动改变结论。README 展示固定提交的来源链接，完整引用保留在研究状态。

`tracked_upstream.max_report_bytes` 默认192000，上限256000；超过上限明确失败。其他来源默认仍使用48000字节限制。示例模型的 `max_prompt_bytes` 调整为524288，以容纳主报告、关联报告和网关代码的联合证据；这是证据大小上限，不代表每次请求都会使用到该上限。

固定上游的“发现日期”直接按报告文件在该仓库中最早可查的提交日期记账（读取提交者日期，最多查询500条路径历史），不要求确认真实发现或引入时间。日期结果持久缓存，单独补全日期不重跑模型；日期接口暂时失败则保留未说明并在后续重试，不阻塞机制评估。

既有历史来源和证据保留，但固定上游模式只自动调度本轮选中的上游报告。发现或抓取失败、模型复核失败、README 推送失败会记录错误；不能把成功读取 GitHub 当作整轮研究成功。切换模式后沿用原状态与模型缓存，不清空已有核验记录。

## 检索与证据

- 示例使用 Google 网页检索，不需要搜索密钥；遇到必须执行 JavaScript 的页面，可安装 Playwright 和 Chromium，在 `search.browser_enabled` 中启用正常浏览器渲染，并通过 `--python` 指定安装该依赖的 Python。验证码不会自动处理，搜索失败会明确报错，不视为“没有新报告”。原有 `bing_rss` 和 `brave` 提供方仍可选，后者读取环境变量 `BRAVE_SEARCH_API_KEY`。
- 每日继续搜索，不以“今天是否升级”作为唯一条件，因此晚发布、晚索引的报告仍能被发现。`seed_urls` 用于补充已知原始报告。
- `required_keywords` 对搜索结果的标题、摘要及 URL 做任一关键词匹配，空列表关闭预筛选；报告真实性仍交给模型核验。已知原始来源优先进入待处理队列。
- `search.enabled: false` 可暂时关闭检索，只验证 `seed_urls` 中的原始报告。模型的结构化阶段结果缓存在私有状态目录，调试校验时复用；原文、代码、模型配置变化后重新请求。错误记录保留校验原因，便于定位未发布的报告。
- 超过每日数量上限的结果进入后续队列。已接受的报告持续检查修订；报告正文或目标源码指纹变化后重新分析。相同内容不重复调用模型。
- 只抓取公网 HTTPS 文本页面；解析并固定连接地址，重定向逐跳重新检查。不执行网页脚本，不下载或运行逆向工具。
- 报告必须经模型判断为相关原创技术分析；文章中的机制、触发条件与版本要引用原文连续片段。确定性检查会核对引用存在，第二次模型复核同时读取原文与源码。此流程提供证据审查，不能保证模型判断永远正确。
- 代码只读取目标 Git 提交中明确配置目录下的普通源码文件，支持 `.mjs`、`.cjs`；不读取本机未提交文件、凭证或链接文件。模型最多选择 12 个文件，配置可指定最多8个 `required_code_paths` 优先读取，合计不超过20个。默认 `max_code_bytes` 为96000，关键实现优先于测试；超出范围或上下文不完整时不得给出确定过滤结论。
- 过滤判断针对适配器已展示的处理路径，不把它与“当前官方 CLI 是否仍生成旧版标记”混为一谈。来源未公开首发日期时，发现时间记录为“未说明”，不拒绝整篇报告。
- 简表短名和摘要仍要求模型尽量精炼；含长英文标识符时，存储分别允许72和240字符，完整内容继续参与独立复核，展示按原宽度压缩，不因字符数略超目标丢弃有效报告。
- 原文或代码引用校验失败时，执行器把具体原因退回模型纠正：代码评估阶段最多两次，其他阶段一次；仍不通过则停止该报告。执行器不会自行修补引用或更改研究结论。
- “发现时间”是本追踪的记账口径：固定 GitHub 上游使用报告文件最早可查提交日期；其他网页保留原报告文章首发日期，不声称是真实首次发现或机制引入时间。执行器读取明确的首发元数据、文章标题前独立日期或 Issue 结构化首发时间；忽略修订时间、评论时间、正文研究日期与抓取日期。元数据矛盾或来源未公开日期时显示未说明，绝不用正文示例日期凑数。单纯更新首发元数据不会重跑已核验的机制与代码分析。
- 如果独立复核否定了机制、版本或触发条件，则最多退回机制提取阶段一次，再完整进行代码评估与复核，而不是反复要求复核改口。再次失败仍保留待处理，不强行发布。

## 机制摘要与证据文档

首页按稳定机制 ID 合并多份报告，同一机制只占一行；不同版本、路径与来源均保留在证据文档。当前报告与历史来源分开，历史来源不参与当前结论合并。有支持的来源互相矛盾时显示“来源结论不一致”，不凭多数票选择结论；尚未核实的来源不冒充相反的确定结论。

分类继续使用隐写、环境标记、协议指纹、模型水印。每项分别记录：

| 维度 | 规则 |
| --- | --- |
| 来源／方向 | 本地客户端到网关、云端 CLI 到服务端、服务端到 CLI、组件内部、多路径或待补充；新方向需要报告连续原文支持 |
| 默认触发 | 默认触发、默认不触发、条件触发、待核实；“未过滤”不能推出默认触发 |
| 网关处理 | 移除、改写、保留、部分处理、不经过网关、待核实；服务端响应不能写成向外上传 |
| 评估状态 | 合并有效来源的静态判断；来源失败、修订或代码变化时保留旧证据并标明待重评 |
| 证据程度 | 固定为报告与源码静态评估；执行器不进行真实流量验证，不允许模型自行升级证据等级 |

旧记录没有方向或独立处理维度时显示待补充／待核实，不根据字段名字编造方向。“已过滤”和“不触发”分别迁移为明确的处理和触发结论。指定报告版本仍作为评估前提，不要求重新逆向 CLI，也不自动发真实推理请求。

`evidence_document` 默认是 `docs/research/README.md`，首页仅显示去重摘要和证据链接。完整条件、原文引用、固定提交的代码链接、审阅时间、报告发现日期与历史来源写入该文件。首次创建后以专用生成标记保护；路径已有手写文档时拒绝覆盖。发现日期按原报告首发或上游首次可查提交记账，不推断机制引入时间。

执行器只替换 README 中 `<!-- termiters:research:start -->` 与 `<!-- termiters:research:end -->` 之间的区域。首页与证据文档以同一个 Git 提交快进发布，原有部署说明和用户工作区不受影响。远端发生并发提交时发布失败，下轮获取最新提交后重试，禁止强推。

## 增量评估与执行状态

固定报告上游可以设置 `tracked_upstream.update_only_on_change: true`（固定上游示例已启用，默认关闭以兼容已有配置）。每天只获取 GitHub 目录和文件 blob ID；只在选定报告或同版本关联报告的内容变化时安排研究。无关提交、目标源码变化、模型配置或执行器升级均不触发模型，也不自动发布 README。此模式下源码变化后的旧评估需通过 `research render` 显式检查和展示，不能将未重新评估的结果视为当前源码已验证。

每份报告及关联内容组合最多自动尝试一次；模型纠错与独立复核仍使用原有单次研究内的有限重试。研究失败的证据和错误保留，`awaiting_upstream_change` 表示等待报告再次变化，不再每天重试。单轮超过 `max_reports` 的未尝试报告继续排队，后续轮次只处理它们。正文下载失败且尚未调用模型时允许重试下载；发布失败可仅重试发布，均不会因此重新调用模型。`--preview` 不推进此模式的生产水位和评估状态，但如有待研究内容仍可能调用模型，不能用它当作零费用检查。

首次启用时没有 `upstream_attempts` 的来源会作为新报告处理。已有部署若希望从当前报告开始静默监测，应先备份状态，核对当前上游提交与已有研究快照一致，再以 `upstream_fingerprints()` 的结果初始化 `upstream_attempts`；不要在未核对版本的情况下跳过新增报告。初始化只改变调度水位，不能把旧失败记录改成成功。后续关闭此开关可恢复原有重评和失败重试行为。

关闭上述开关时沿用以下重评策略。新评估保存实际提供给模型的代码文件及必读入口的 Git blob ID。只有这些文件变化才重新评估；证据不全或旧记录没有文件依赖时仍保守使用整体源码哈希。代码变化但报告及评估口径未变时，复用通过校验的机制提取结果，只重跑评估与复核；复核否定机制提取时仍回退到提取阶段纠正。新协议字段上线后，即使报告及代码哈希未变，缺失方向、触发或处理字段的旧记录也必须回填；已接受的旧报告优先使用现有报告预算，失败后回到正常重试队列，不自动扩量。新模型结果必须显式提供三个字段，确有证据缺口时填写 unknown 并说明理由。原报告及默认源码足以支持的条件结论无需以真实抓包为前提。同一机制涉及多个通道时分别说明触发条件。

报告分别保存结果。失败来源保留历史结论但标为待重评；新报告失败不产生机制结论。运行结果区分 `complete`、`partial`、`failed`，发布另记 `published`、`unchanged`、`preview`、`failed` 或 `no_evidence`。报告排队或部分失败有有效证据时属于部分完成，Rust 入口正常返回并提示查看运行记录；没有任何有效证据的错误、发布失败和执行器异常仍报失败。这样不会把“成功发布部分结果”冒充完整研究，也不会丢掉已经核验的材料。

`last-run.json` 保留研究执行信息、错误与队列数量；仅渲染的结果写入 `last-render.json`，不覆盖研究历史。README 不包含重试次数、队列顺序或每次轮询时间，输出没有实质变化时不创建提交。

## 不调用模型的快照检查

```sh
# 完全离线，使用已有裸仓库与状态库，强制只生成预览。
TermiteRS research render --config /etc/termiters-research/research.json --offline

# 获取目标仓库最新提交后渲染；不抓取研究报告、不调用模型、不发布。
TermiteRS research render --config /etc/termiters-research/research.json

# 审阅通过后发布已有证据生成的快照，配置中 publish 也必须为 true。
TermiteRS research render --config /etc/termiters-research/research.json --publish
```

预览保存在状态目录的 `README.preview.md` 与 `research-evidence.preview.md`。`--offline` 与 `--publish` 互斥。渲染会检查当前源码有效性，但不会把旧结论补写成新验证结果。展示中“旧记录待回填”表示字段尚未结构化，“证据不足／待核实”表示已评估但依据不足，“待重评”表示旧结论失效或核验未完成；原报告来源独立保留。

## Linux 每日运行

`deploy/termiters-research.service` 与 `.timer` 是待安装模板。配置运行用户 `termiters`、模型环境文件 `/etc/termiters/research.env`、Git 推送凭据和 `/var/lib/termiters` 写权限后，将模板安装到 `/etc/systemd/system/`。模型密钥只放环境文件，权限设为 `0600`。

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now termiters-research.timer
systemctl list-timers termiters-research.timer
journalctl -u termiters-research.service
```

默认每天 03:00 UTC 后随机延迟最多 15 分钟。停机错过的轮次在恢复后补跑一次。每轮最多 2 小时，进程退出后释放锁；同一状态目录的重叠运行会失败退出。关键词、每日数量、联网与模型超时、是否发布均可配置。部分完成写入执行记录并输出明确提示；执行或发布失败让 systemd 显示失败。下一天按原预算继续重试。
